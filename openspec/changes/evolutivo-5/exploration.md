### Constraints and cross-cutting findings

1. **Payment immutability today** is enforced only by two guards in `routes/transactions.js` (:232, :418). Reversal does not violate it if it is a dedicated endpoint; the guards stay and the messages should point to "Revertir pago".
2. **No soft-void**: 26 `findAll('transactions')` call sites (ledger balances, summary, trends, goals, economics, alerts forecast...) would all need a `voidedAt` filter. The rent undo precedent removes the transaction and keeps a tombstone (`rentCollections.reversedAt`, `reversedTransactionId`; `rent-collections.js:227`). Follow it.
3. **Activity log** is route-table driven. Every new write endpoint needs an `ROUTES` entry or it is logged as "Realizaste un cambio en ..." (including any POST "preview"). New entries: payment revert, modality end, rental delete, document delete, note update/delete. `tests/services/activity-log.test.js` enumerates actions.
4. **"Vigente"** is ambiguous: `settle`/`activeContractsFor` consider `status==='active'` (including a future-dated rental that does not overlap). Backend permits declaring a non-overlapping rental while another is active (`rental-declarations.js:254`); the request wants the button disabled when one is in force (UI-only block; backend rules stay).
5. **`GET` endpoints write**: `contractResponse` / `view(... occurrences)` call `generateOccurrences`, which persists rows (12 months ahead). Fine for existing flows; new list endpoints (history, periods) should use `alerts.readOnlyView(db)` as `obligationHistory`/`monthlyView` do, except where a persisted id is needed for an action (period actions need real occurrence ids; `virtual:` ids cannot be collected).
6. **Pagination/perf**: rent occurrences are generated per contract up to `through`; `occurrenceDates` caps at 1200. A history/periods builder with unbounded year range is fine for this data size (JSON files, single user) but the 120-month clamp in `obligationHistory` and `monthlyView` (error "El rango no puede superar los 120 meses") must be replaced by a year-based window (request: "no artificial limit; communicate if kept").
7. **Documents of a rental**: documents link by `contractId` (per modality), `rentOccurrenceId`, `transactionId`, `assetId`. There is no declaration-level target. A "rental Documentos tab" is therefore an aggregate over the declaration's contracts+occurrences+collections unless a `declarationId` target is added.
8. **Notes**: `wealthNotes` targets `asset|entity|obligation|contract|rentOccurrence|rentCollection` (`wealth-notes.js:16-35`); declaration has its own `notes` (4000 chars, editable via "Editar alquiler").
9. **Tenant resolution annul** already exists: `DELETE /obligations/:id/occurrences/:occId/resolution` -> status `voided` (`obligations.js:531`), button "Anular resolución" at `obligations.js:~191`; needs confirmation and exposure in Períodos/Avisos only.
10. **Cancel period** exists: `POST /rentals/:id/occurrences/:occId/cancel` (`routes/rentals.js:165`); needs confirmation + reworded 409.

### Approaches

**A. Payment reversal storage**
1. **Tombstone + remove transaction** (recommended) — snapshot the payment into a new `obligationPaymentReversals` collection (`transactionSnapshot`, `occurrenceId`, `reason`, `reversedAt`, `documentIds`, idempotency key hash), remove the transaction, update reconciliation. Pros: balances/summary/savings/alerts correct with zero changes to the 26 consumers; same pattern as rent undo; occurrence state auto-recomputes. Cons: new collection (needs registration in `jsondb`/migrations list), history must read tombstones to show "Revertido". Effort M.
2. **Soft-void flag** (`voidedAt` on the transaction) — keeps one record. Cons: every consumer of `transactions` must exclude it (26 sites + tests), high regression risk. Effort L/risky.
3. **Compensating movement** (status quo) — does not satisfy "anular el gasto". Rejected by the request.

**B. History read model**
1. **New `GET /assets/:id/history?year=&month=`** (recommended) — one server builder emitting typed rows (obligation, rent, adjustment, event, reversal) with `years[]`; old `obligation-history` kept (tests pin it). Cons: more backend code. Effort L.
2. Extend `obligation-history` — breaks its pinned key set and mixes concerns.
3. Compose client-side from `obligation-history` + `rentals` + `monthly-view` — three fetches, duplicate logic, inconsistent states. Rejected.

**C. Rental modal code organization**
1. **New file `rentalModal.js` (+ small helpers)**, `assets.js` keeps list/ficha/history (recommended): removes 700+ lines from `assets.js`, avoids growing a 1311-line object; costs re-pointing ~6 source-slicing tests and adding script tag + sw entry. Effort M.
2. Keep everything in `assets.js` — fewer test edits now but ~2000+ lines and slicing tests stay fragile. Not recommended.

**D. Periods builder**
1. **Single server builder `GET /rentals/declarations/:id/periods`** reused by Períodos tab, Resumen progress, ficha mensual modal, ficha rental summary (recommended). Effort L but removes duplication.
2. Client merges `/rentals/months` + `/obligations` + collections — repeats the current duplication the request wants gone.

- **Size**: ~9x the review budget; need a delivery decision (chained PRs by wave, or one PR with `size:exception` like evolutivo-4).
- **Revert correctness**: dependents (refund, normalization, allocation, claim/recovery), reconciliation reset, idempotency-key replay after revert, receipts left dangling on the removed transaction, partial payments (revert one of several), rollback on failure (use the `atomically`/snapshot pattern from `rent-collections.js:21`). Needs a test for each of savings/balance/month expense after revert.
- **Rental deletion** can orphan income if collections exist; default must block (see Q2).
- **Contract end via `PUT /rentals/:id`** skips `settle` today (asset stays "rented" after ending the last modality); the new modality-end endpoint must replace the UI path, otherwise the inconsistency persists.
- **Adjustment rule vs. request**: current `applyCondition` rejects the whole update if any occurrence at/after the effective date has collections; the request says "apply to future non-collected periods". Behavior change affects `rentals-adjustment` tests.
- **GET side effects** on read endpoints (occurrence generation) and `virtual:` ids: a builder that is read-only cannot offer actions on not-yet-persisted occurrences (collect/cancel need persisted ids).
- **Brittle contract tests**: ~12 test files slice `assets.js`; splitting files or reordering methods silently breaks them. Update them in the same unit that moves the code.
- **Service worker / static assets**: new JS files must be added to `index.html` and `sw.js` `STATIC_ASSETS` and the cache name bumped, else users keep stale code (tests pin v41 until release).
- **Accessibility/responsive scope** (tabs, focus trap in nested `Modal.push`, tables as mobile cards) is non-trivial: Modal focus trap only handles the top layer; nested receipt/detail modals must restore focus.
- **Logs**: any endpoint without a `ROUTES` entry is logged generically; a POST preview would be logged as a write.
- **No `uploadedBy`** on documents ("quién cargó"), no note `title`: both are schema additions (additive, no migration).

### Open product questions (suggested defaults)

- **Q1 Delivery**: single PR over budget? Default: chained PRs in 3 waves (W1-W2 / W3-W6 / W7-W11) or single PR with recorded `size:exception` as in evolutivo-4. Needs the user's decision before `sdd-tasks`.
- **Q2 Delete rental with collections** (request is contradictory: "warn if it has collections" yet "revert/immutable ledger"): default = block while non-reversed collections exist ("Deshacé los cobros primero"); allow with periods/documents/notes after a stronger warning; block while active (finish first).
- **Q3 Edit historical rental**: default = open the existing edit modal only when the declaration has no collections, documents or linked obligations; otherwise read-only.
- **Q4 Where do "Otros movimientos atribuidos" and "Cobros y saldos no aplicados" go?** Default = ficha economics block (attributed movements) and the Períodos detail (collections per period); unapplied balance shown as a note on the period of the collection.
- **Q5 "Vigente"**: default = declaration with any contract `status==='active'`; header state: Activo / Próximo a vencer (end date within 30 days, same as alerts) / Finalizado; a future-start rental shows "Próximo a iniciar" only as a label.
- **Q6 Declare while one is active**: default = UI disables it with "Finalizá el alquiler vigente antes de declarar uno nuevo"; backend still allows non-overlapping rentals (API untouched).
- **Q7 History year/month scope**: default = year selector lists years from earliest asset/obligation/rental date to the current year (plus next year if future rent exists); "Todo el año" shows 12 months; drop the 120-month cap on the history endpoint but keep it on `monthly-view`.
- **Q8 Revert partial payments**: default = revert individual payment (by `paymentId`), not the whole occurrence; block when the payment has dependents.
- **Q9 Receipts on a reverted payment**: default = keep them attached to the reverted record (visible in history as "Revertido"); no delete option during reversal.
- **Q10 Revert in Avisos**: Avisos does not list payments; default = only on `document_pending` alerts (paid occurrence missing receipt) via the payment detail.
- **Q11 Tenant payments**: "Revertir pago" only for owner payments; "Anular resolución" for tenant resolutions (already supported).
- **Q12 Rental-level documents/notes**: default = aggregate of the declaration's contracts/occurrences/collections, upload goes to the selected modality's contract; add optional `title` to notes and `declarationId` target only if W7 design chooses it.
- **Q13 Version**: default v1.13.0, sw cache v42.
