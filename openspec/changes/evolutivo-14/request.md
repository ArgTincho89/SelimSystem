# Evolutivo 14 — Two-step movement attribution and paying a due date from the transaction form

> Branch: `evolutivo-14`. Delivery: PR to master, merge after CI green, deploy (follow-up to evolutivo-13). Release 1.20.0 (includes the 1.19.1 monthly-frequency default).

## Request (summary of the user's words)
- "Atribución del movimiento" is one giant select with every asset, obligation, due date, contract and rent period. Redesign it in two steps: first **Bien** (assets only, plus "Sin atribución" and an "Obligaciones sin bien" entry), then an optional **"Obligación o período (opcional)"** that only lists what belongs to the chosen bien (obligations, due dates labelled "Vencimiento · <título> · dd/mm/aaaa · pendiente $X", rental contracts, rent periods). Choosing only the bien is enough. Keep amount, Quitar and "Asignación completa". Mobile friendly. Editing preselects bien and detail.
- Second payment path: an **expense** attributed to a due date must be registered as a **payment** of that due date, exactly as "Registrar pago" (same records, totalPaid/status, partial payments, audit entry, receipts, alerts). Reuse the payment service; validate amount > 0, amount ≤ remaining and account currency = obligation currency; nothing written on error. Hint "Se registrará como pago de este vencimiento". Incomes/refunds never pay; rent periods/contracts stay informational. Decide multiple due-date rows and editing existing transactions.

## Decisions
- D1: The payment logic of `POST /api/obligations/:id/occurrences/:occurrenceId/payments` moved, unchanged, to `src/services/obligation-payments.js` (`register` + `activityMeta`). The obligation route and the transaction route both call it: same validation order and messages, same transaction shape (`obligationId`, `obligationOccurrenceId`, `obligationIdempotencyKey`, `obligationPaymentFingerprint`, `paymentId`), same idempotency and reverted-key rules. The dialog fingerprint is unchanged; the form adds its extra fields (`clasificacion`, IVA) to the fingerprint only when present, so older replays still match.
- D2: The transaction form sends `obligationPayment: { occurrenceId, idempotencyKey }` in `POST /api/transactions`. The server validates every ordinary field first, then requires `tipo: expense`, no recurrence and no installments, and maps the form to the payment input: amount = `monto`, account, category, date = `fecha` (not future), method = `paymentMethod`, title = `titulo` (empty falls back to the due date title), notes = `comments` (required: "Los comentarios son obligatorios para registrar el pago de un vencimiento"). The idempotency key is generated once per opened form (a double click replays, answering 200 with `replayed: true`).
- D3: The payment model links one transaction to one occurrence and counts the whole transaction amount as paid. So a payment is the **whole movement**: one due-date row per expense, as its only attribution row, with an amount equal to "Monto" (prefilled when the due date is chosen). Several due-date rows are rejected with "Un gasto puede pagar un solo vencimiento: registrá un gasto por cada vencimiento".
- D4: A payment created from the form stores **no** `movementAllocations` row: the payment link already attributes it to the obligation's asset in the economic analysis, and an allocation would make "Revertir pago" refuse it as a dependent movement. Reverting is therefore identical to a dialog payment (`PUT`/`DELETE /api/transactions/:id` still answer 409, "Revertir pago" removes it and the due date goes back to pending).
- D5: Audit log: a new `POST /transactions` route entry with action `obligation.payment` (selected through `res.locals.activityMeta.action`) writes the same message, metadata and undo descriptor as "Registrar pago"; entity type stays `transaction` (the created movement). Receipts attached in the form are uploaded with `{ transactionId, occurrenceId }`, like the payment dialog.
- D6: Editing an existing transaction never converts it into a payment (the payment model cannot link an existing movement and payments are immutable). In edit mode due dates are informational: other due dates are shown disabled, the stored one stays selectable, and the hint says "Para registrar el pago de un movimiento existente usá Registrar pago". Stored descriptive allocations keep saving as before.
- D7: The detail select depends on the type: expenses list the bien's obligations and their pending due dates (not cancelled, remaining > 0); incomes list its rental contracts and rent periods (informational, as before); refunds only "Solo el bien" (refund allocations are not saved, as before). "Obligaciones sin bien" is offered only for expenses and only when such obligations exist; choosing it requires picking an obligation or due date.
- D8: Installments keep accepting only one asset-level attribution (no detail), as before.
- D9: Version 1.20.0 folds the 1.19.1 change; service worker cache stays v55.
